Vom Tool-Chaos zum MCP-Handshake

Drei Zonen, drei Tabs: vom unstrukturierten Werkzeug-Wirrwarr über das strukturierende Server-Schema bis zum präzisen, Schritt-für-Schritt nachvollziehbaren Handshake.

🌋 Zone 1 — Sammeln

Das N×M-Problem

Vor einem gemeinsamen Standard musste jede KI-Anwendung für jedes Werkzeug eine eigene, maßgeschneiderte Verbindung bauen. Kein Muster, keine Struktur — nur Einzelfälle, die sich nicht wiederverwenden lassen.

🗺️ Zone 2 — Strukturieren

Der MCP-Server als Übersetzer

MCP führt drei feste Rollen ein. Der Host ist die Anwendung, in der du arbeitest (z. B. Claude). Er startet für jeden Dienst einen eigenen Client, der jeweils genau eine Verbindung zu einem Server hält — und dieser Server übersetzt die Fähigkeiten eines Diensts in ein einheitliches Schema.

RolleAufgabeBeispiel
HostDie Anwendung, in der du arbeitest — verwaltet alle Client-Verbindungen und führt Ergebnisse zusammen.Claude-App, Claude Code
ClientHält genau eine 1:1-Verbindung zu einem Server — kennt nur diesen einen.ein Client pro Dienst
ServerÜbersetzt die Fähigkeiten eines Diensts in Resources, Tools und Prompts.Notion-Server, Figma-Server

Ein Host, mehrere Server — aber strikt getrennt

Jeder neue Dienst bekommt einen eigenen Client. Tippe, um Server nacheinander zu verbinden, und beobachte, wie der Host wächst — ohne dass sich die Server je begegnen.

Host
Claude-App
Wichtig: Jeder Client kennt nur seinen eigenen Server. Der Notion-Client sieht keine Figma-Daten und umgekehrt — der Host sieht nur, was jeder Client ihm zurückmeldet. Diese Isolation ist ein zentrales Sicherheitsprinzip von MCP.

Die gemeinsame Sprache unter jeder dieser Verbindungen ist immer dieselbe: JSON-RPC 2.0 — ein schlankes Nachrichtenformat, egal ob lokal über stdio (Server läuft auf demselben Rechner) oder entfernt über Streamable HTTP (Server liegt im Netz, wie bei den meisten deiner Notion- oder Figma-Verbindungen).

🎯 Zone 3 — Spezifizieren

Der Handshake — Schritt für Schritt

Vier Schritte, die aus einer vagen Absicht eine präzise, aufrufbare Fähigkeit machen. Mit „Weiter“ durchklicken.

Claude
(Client)
Notion-
Server

1 · Initialize — wer bist du, was kannst du?

Der Client stellt sich vor und nennt die Protokoll-Version. Noch ist nichts vereinbart — nur die Anfrage steht.

// Client → Server
method: "initialize"
protocolVersion: "2025-06-18"
clientInfo: { name: "Claude", version: "…" }

2 · Bestätigung — der Server meldet seine Fähigkeiten

Der Server antwortet mit genau den Fähigkeiten, die er unterstützt. Beide Seiten kennen jetzt die gemeinsame Basis — mehr nicht, weniger nicht.

// Server → Client
capabilities: { tools: {}, resources: {}, prompts: {} }
serverInfo: { name: "Notion-Server", version: "…" }

// Client → Server (Bestätigung)
notification: "initialized"

3 · Discovery — was genau bietest du an?

Erst jetzt fragt der Client konkret nach: Welche Tools gibt es, mit welchen Parametern? Aus „irgendwas mit Notion“ wird eine Liste benannter Fähigkeiten.

// Client → Server
method: "tools/list"

// Server → Client
tool: create_page(parent_id, title, content)
tool: query_database(database_id, filter)

4 · Aufruf — die Fähigkeit wird genutzt

Der Client ruft ein konkretes Tool mit konkreten Parametern auf. Das ist der Klarheits-Sprung: aus einer vagen Absicht ist eine präzise, testbare Aktion geworden.

// Client → Server
method: "tools/call"
name: "create_page"
arguments: { title: "Moderationsleitfaden", … }
✦ Klarheits-Sprung: aus „irgendwie verbinden“ wird eine präzise, aufrufbare Fähigkeit

Systemprompt

Rolle: Du bist Trainer:in für AI-Literacy und begleitest Teilnehmende dabei, das Model Context Protocol (MCP) über das Denkraum-Modell zu verstehen — von der unstrukturierten Zone 1 (Sammeln) über die musterbildende Zone 2 (Strukturieren) bis zur präzisen Zone 3 (Spezifizieren).

Ziel: Teilnehmende sollen sowohl das N×M-Problem als auch den vierstufigen Handshake (Initialize, Bestätigung, Discovery, Aufruf) in eigenen Worten erklären können.

Handbuch
  • Einsatzdauer: ca. 15–20 Minuten als Opener oder Zwischenmodul, ein Tab pro Zone.
  • Zone 1: Button „Verbindungen sichtbar machen“ tippen, dann die drei Konsequenz-Karten besprechen.
  • Zone 2: Rollen-Tabelle kurz erklären, dann per „+ Server verbinden“ alle drei Server nacheinander hinzufügen lassen — die Isolations-Hinweisbox erscheint automatisch ab dem zweiten Server. Danach alle drei Bausteine-Karten aufklappen lassen.
  • Zone 3: Die vier Schritte mit „Weiter“ gemeinsam durchklicken — der Klarheits-Sprung-Badge erscheint erst nach Schritt 4.
  • Abschluss: Reflexionsfrage im Plenum oder in Kleingruppen besprechen.
Vortrags-Skript

„Bevor es einen gemeinsamen Standard gab, musste jede KI-Anwendung jedes Werkzeug einzeln kennenlernen. Das nennt man das N×M-Problem — reine Zone 1: Sammeln, ohne Struktur. Und das kostet nicht nur beim Bauen, sondern bei jeder Wartung neu.

MCP führt drei feste Rollen ein: Host, Client, Server — verbunden über eine gemeinsame Sprache, JSON-RPC. Für jeden Dienst gibt es einen eigenen Client mit genau einer 1:1-Verbindung. Das ist mehr als Ordnung — es ist ein Sicherheitsprinzip: Ein Notion-Client sieht niemals Figma-Daten, weil er den Figma-Server gar nicht kennt. Jeder Server bietet außerdem drei wiederkehrende Bausteine: Resources zum Lesen, Tools zum Handeln, Prompts als Vorlagen. Das ist Zone 2 — Strukturieren.

Der eigentliche Klarheits-Sprung passiert im Handshake, Schritt für Schritt: Erst stellt sich der Client vor, dann bestätigt der Server seine Fähigkeiten, dann fragt der Client konkret nach dem Angebot — und erst dann wird eine Fähigkeit tatsächlich aufgerufen. Aus vagem Zugriffswunsch wird eine präzise, testbare Aktion — Zone 3.“

Normen-Register
  • Model Context Protocol (MCP) — offener Standard, veröffentlicht von Anthropic im November 2024, mittlerweile an die Agentic AI Foundation der Linux Foundation übergeben.
  • Transportebene: JSON-RPC 2.0, Verbindungstypen stdio (lokal) und Streamable HTTP (entfernt).
  • Bezug zum Denkraum-Modell: eigenes, IREB-orientiertes Coaching-Framework von Michaela Kühn (keine externe Norm).
  • Hinweis: Protokollversion und Spezifikationsstand vor jedem Einsatz gegen die aktuelle Quelle prüfen, da MCP sich aktiv weiterentwickelt.
